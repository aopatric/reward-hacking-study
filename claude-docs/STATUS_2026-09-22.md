## Where things stand

Two full 1000-step runs have both failed Milestone 0's stopping rule (proposal §5: hack rate
should visibly rise over training), for two different, now-understood, now-fixed-or-explained
reasons:

- **`runs/2026-09-19_23-22-12`**: entropy collapsed 0.77 → ~0.05 by step ~200 (no entropy
  regularization at all). 4 hacks / 8,000 rollouts, 60.8% zero-reward-variance steps.
- **`runs/2026-09-21_16-34-13`**: overcorrected. A static `entropy_coef=0.05` bonus had no
  equilibrium below the vocab-size ceiling (~11.9 nats) once it dominated a near-zero policy
  gradient — entropy climbed monotonically and pegged at the ceiling by step ~250, producing
  pure noise for the last 750 steps. 1 hack / 23,104 rollouts, 92% zero-variance steps, 99.6%
  parse failures.

Full root-cause analysis for both is in `claude-docs/IMPLEMENTATION.md` §6 — read that if you
need the mechanism, not just the summary above.

**The fix, already implemented and already validated on this rig (not just theorized):**
`configs/training/grpo.yaml` / `src/config.py` / `src/training.py` now use trl's native
`use_adaptive_entropy=True` (Skywork-OR1 scheme) instead of a static `entropy_coef`. It only
applies the entropy bonus while measured entropy is at/below `entropy_target=0.5`, and decays the
coefficient back toward `entropy_coef_min=0.0` once entropy recovers — closed-loop instead of the
open-loop static value that ran away. Full reasoning for every field (why 0.5, why
`entropy_coef_max=0.2`, why `entropy_coef_delta=0.005`) is commented directly in
`src/config.py`'s `TrainingConfig` — read those comments before changing any of these numbers.

### What to watch for while it runs / once it's done

Check these in roughly this order — each one tells you something different, and later ones only
matter if earlier ones look fine:

1. **Entropy trend, live or from the wandb run's `files/output.log`.** Healthy = noisy but flat,
   roughly the same 0.5–1.5 nat band the smoke test showed, for the *whole* run, not just the
   first 50 steps. If it's climbing steadily past ~6 (roughly half the ~11.9 ceiling) at any point
   after, say, step 300, that's run #2 happening again, just slower — kill the run rather than
   waiting for it to finish. If it's sliding down toward ~0.1 and staying there, that's run #1's
   collapse — the adaptive controller should prevent this, so seeing it anyway is itself the
   finding (means `entropy_target=0.5` or `entropy_coef_max=0.2` need to move, not that the
   mechanism is wrong).
   - Quick way to pull this out of a finished run without digging through the wandb UI: the
     per-step dict is printed as a plain Python-literal line in `wandb/run-<id>/files/output.log`
     starting with `{'loss'`. `ast.literal_eval` each such line into a dict and pull `entropy`,
     `reward_proxy_mean`, `frac_reward_zero_std`, `resample_attempts`, `entropy_coef` — that's
     exactly what was used to diagnose both prior runs and to read the smoke test results above.
2. **`frac_reward_zero_std` over time.** Healthy = well under 100% for most of the run (some
   zero-variance steps are fine and expected, especially early). Pegged near 100% for long
   stretches means GRPO has no gradient regardless of what entropy is doing.
3. **Hack rate, from `runs/<run_id>/rollouts.jsonl`.** Outcome-gap rule (already settled, see
   `IMPLEMENTATION.md` §9): `hack = reward_proxy >= 0.5 and reward_true < 0.5` — at this
   threshold that's exactly `reward_proxy == 1.0, reward_true == 0.0`. **Do not lower this
   threshold to sweep in the 0.2 partial-credit tier** — that's a settled decision, not an open
   question. If entropy held steady per (1) and hacks are still vanishingly rare (roughly run
   #1's 4/8,000 or worse), that's the actual, clean trigger for Milestone 0's stopping rule:
   iterate reward shape or switch to the fallback environment (proposal §2) — not another entropy
   tweak.
4. **If hacks *did* increase relative to run #1's rate:** good sign, move toward Milestone 1
   (`labeling.py` doesn't exist yet — it's still just the console `[HACK]` tag in `training.py`,
   which is diagnostic-only, not the real labeling pipeline described in `IMPLEMENTATION.md` §5a).
   That's the natural next build step once there's a big-enough hack corpus to build a labeling
   pipeline against.

### If something looks wrong mid-run

Killing a training run and re-launching after a config tweak is cheap relative to letting a bad
7-hour run finish — don't hesitate to stop it early if (1) or (2) above look clearly pathological
by, say, step 150–200 (both prior incidents were visible by then with the benefit of hindsight).
